# T3 Ops Copilot

**HackSHSID 2026 · Track 3 (Accenture)** — a facts-first decision-support assistant for an airline disruption
desk at eight fictional airports. It computes the evidence, drafts the advice, and keeps every operational
decision with a qualified human.

> **模拟 / SIMULATED.** Every airport, event, weather value and number in this project is fictional, generated by
> the organizers (`Track 3 Data.xlsx`). The assistant gives decision support only: flight safety, release,
> cancellation, dispatch, maintenance and compensation decisions stay with qualified people, and passenger drafts
> are reviewed by a person before anything is sent.

**Measured, not asserted:** `21/21` exam cases · `56/56` unit tests · 192 airport-months · 13 output checks ·
offline Python-stdlib app · no API key required.

---

## The thesis in one sentence

Most AI assistants generate an answer and hope it is right. **This one computes the facts first, makes the
language model optional, and lets a deterministic checker block any number, action or claim that cannot be
traced.** The result is not a chatbot that talks about operations — it is a small, auditable decision-support
system that happens to write well.

---

## Eight design choices that make this more than a chatbot wrapper

### 1. Facts are computed, never generated
The workbook is read once; Python builds a **fact sheet** in which every value carries a source ID
(`SIM-BASE`, `SIM-WEATHER`, `SIM-SCALE`, `RULE00x`, `EVT00x`). The writer only turns those facts into prose.
It cannot introduce a number because the **checker verifies every numeric claim against the fact sheet** before
the output reaches a person.
**Why this is thoughtful:** the usual failure mode of AI in operations is a confident sentence with a number
that nobody can find. Here, arithmetic is a code responsibility and language is a writing responsibility.

### 2. The detector has a control group
A single rule — “5 points below the airport's own average” — flags **12 airport-months**, 11 of them in the
July/August summer dip. That is not actionable. Our detector adds two independent controls:

- **same-size peers** — is the whole tier moving, or just this airport?
- **the same month last year** — is this a seasonal pattern, or a genuine break?

The result is designed to disagree with the naive rule when the naive rule is wrong. Hailing 2025-07 trips
**all three** comparisons (`−15.62` pp vs its own average, `−5.46` pp vs same-size peers, `−11.48` pp vs last
year) and is the only 3-signal month in the entire dataset. Yunchuan's July looks bad on its own average
(`−6.07` pp) but is **−0.80 pp year-on-year** — seasonal, not unusual — so the detector clears it.
**Why this is thoughtful:** it answers “which alert is serious?” with evidence, not with a threshold.

### 3. Uncertainty is a first-class product outcome
The risk ladder is `normal → watch → unusual → clearly unusual`, plus **`Can't tell`**. The engine degrades
confidence when a comparison is unavailable or a weather record is missing (four organizer rows are marked
missing), and it never imputes a weather value. When EVT003 reports two conflicting sources, the output is
`Can't tell`, and the first action is to verify which source has been reviewed and whether both use the same
statistical definition.
**Why this is thoughtful:** “I can't tell yet” is often the most useful and most honest answer an operations
assistant can give. We treat it as a designed outcome, not an error.

### 4. Human authority is enforced by the architecture
The assistant's action space is closed. Cancelling, releasing, dispatching, maintaining or compensating flights
is **removed** from what it may do (`RULE007`), and field **f12** lists those decisions as explicitly human.
Passenger messages are drafts only. Accept / Edit / Reject with a reason is appended to an append-only memory
and quoted the next time a similar event appears.
**Why this is thoughtful:** “human in the loop” is usually a sentence in a slide. Here it is a constraint in the
code, a required field in the output, and a record that survives the decision.

### 5. Evaluation is adversarial by construction
The exam is not a demo script. The same `engine.pipeline` used by the website is driven through:

- **15 official organizer tests**,
- **5 of our own unseen events**, including a hostile input that tries to force a cancellation, asserts
  weather causation and includes a passenger name and phone number,
- **1 fabricated-number negative test** that requires the checker to block the bad writer.

There is no answer bank and no separate “test mode”. The runner reports must/must-not failures, and it refuses
to invent a pass. The supporting unit suite covers detector truth, fact-sheet privacy, checker behavior and the
runner itself.
**Why this is thoughtful:** the evaluation is designed to find weakness, not to produce a pleasing score.

### 6. Traceability is structural, not a disclaimer
Every fact in the output is linked to a source ID and every number is checkable. The 17-field advice keeps the
organizer's own template and Chinese labels; assumptions, unknowns and missing data are separated instead of
blurred into prose. The checker's 13 checks cover field completeness, number traceability, source validity,
committed actions, passenger-message safety, PII, the simulated label, conflict handling, missing weather,
feedback recall, causal overclaims and the human-decision field.
**Why this is thoughtful:** a reviewer can audit the output without trusting the model. The claim “every number
has a receipt” is testable.

### 7. The demo is operationally real
The app is a **single-command, offline, standard-library web app**: no network, no API key, no build step, no
CDN. The offline template writer is deterministic, so the same input produces the same advice. `data/track3.json`
is committed and rebuilds byte-identically from the workbook. A bad writer mode exists so the checker can be
demonstrated blocking a fabricated “20 points” claim.
**Why this is thoughtful:** an operations tool that needs the internet, a key and a clean demo god is not an
operations tool. Ours works on a laptop with the network unplugged.

### 8. Bilingual by design, not bolted on
The UI switches between **English and 中文**, and the 17-field output keeps the organizer's Chinese labels
alongside the English content.
**Why this is thoughtful:** the people who would use this tool and the people who set the task do not
necessarily read the same language. A bilingual interface is a usability decision, not a translation afterthought.

## Who it is for (airline voice)

This is the operations assistant for **our airline's disruption desk** — one fictional Chinese domestic airline.
Priority combines **anomaly with importance to our airline**: a large drop at a high-importance airport matters
more than a similar drop at a small one. Field **f14** is the message to the **airport coordination team**;
field f13 is for our own operations staff and field f15 is the passenger draft. Decisions on cancellation,
release, dispatch, maintenance and compensation stay with our airline's qualified staff; the assistant only
prepares evidence and drafts for a human.

## What it is: four layers, one product

1. **Detector — “is this unusual?”** Three comparisons for each airport-month (own trailing 12-month average,
   same-size peers, same month last year). Each comparison at least 5.00 percentage points below its baseline is
   one signal; 0–3 signals produce `normal / watch / unusual / clearly unusual`, with a confidence value.
2. **Fact sheet → writer → checker.** Python computes the facts and source IDs. The deterministic offline writer
   turns the fact sheet into the organizer's 17-field advice plus three audience drafts. The checker verifies
   numbers, sources, actions, PII, causal claims and the simulated label.
3. **Exam.** `tests/run_tests.py` drives the same `engine.pipeline` the website uses — no answer bank — through
   the 15 official tests, 5 of our own unseen events and a fabricated-number negative test.
4. **Feedback memory.** Accept / Edit / Reject plus a reason is appended to `data/feedback.jsonl` (never
   overwritten) and quoted the next time a similar event is analysed.

Every page and output carries the `模拟 / SIMULATED` label.

## How the detector earns its verdict

The official rule is the starting point, not the answer. Our three comparisons are:

| Comparison | Baseline | What it controls for |
|---|---|---|
| Own history | the airport's trailing 12-month average | the airport's normal level |
| Same-size peers | average of airports in the same size tier | network-wide shocks |
| Same month last year | the same airport-month in 2024 | seasonality |

A month is a signal when it lands at least 5.00 pp below that baseline. Hailing 2025-07 is the clearest case:

| Airport-month | vs own average | vs peers | vs last year | Signals | Verdict |
|---|---|---|---|---|---|
| Hailing 2025-07 | **−15.62 pp** | **−5.46 pp** | **−11.48 pp** | **3 / 3** | **clearly unusual** |
| Hailing 2025-08 | −10.99 pp | −3.66 pp | −9.14 pp | 2 / 3 | unusual |
| Yunchuan 2025-07 | −6.07 pp | +5.47 pp | **−0.80 pp** | 1 / 3 | watch — seasonal, cleared |

The network matters too: July/August average completion (78.8 / 78.5 %) is naturally lower than March (84.3 %).
That is why the detector does not treat a summer dip as an emergency on its own.

## How the checker protects the output

The checker is deterministic and runs after every output; a failed run is visible, not hidden. Its 13 checks cover:

- all 17 fields present and non-empty,
- every number traceable to the fact sheet,
- every `[FACT: …]` source valid,
- no committed action (“has been cancelled / sent”) and no assistant decision outside f12,
- passenger draft wording: draft, official channels, no asserted delay,
- three pairwise-distinct audience messages,
- no mobile number, ID number or email,
- `模拟` present in the three message fields and the status field,
- conflict shown as `Can't tell`,
- missing weather disclosed, never imputed,
- prior feedback quoted when one exists,
- no unhedged weather-causation claim,
- f12 lists the human decisions (cancel / release / dispatch / maintain / compensate).

A failure produces a clear list of what failed, and the UI shows the failed checks rather than hiding them. The
bad-AI demo exists precisely so this mechanism can be shown live.

## Data and limits

- All data is simulated: 8 fictional airports × 24 months = 192 airport-months, 12 rules, 15 official tests,
  5 events, 3 feedback seeds. English airport names are our transliterations.
- Data-quality intents: **DQ001** everything simulated · **DQ002** four missing weather rows (Qinglan 2025-03,
  Gaoyuan 2025-09, Hailing 2025-11, Linjiang 2025-11) · **DQ003** EVT003 has conflicting sources — the honest
  answer is `Can't tell` · **DQ004** Hailing 2025-07/08 is a planted anomaly, not a real-world event.
- Monthly airport-level data cannot identify individual flights, crews or gates; weather is background evidence,
  not proof of causation. Never read the app's numbers as real operations data.
- The detector reproduces the organizer workbook exactly: 192 airport-months; 12 own-history flags; 13 any-signal
  months; signal counts `{0: 179, 1: 11, 2: 1, 3: 1}`; Hailing 2025-07 = −15.62 pp vs own average, −5.46 pp vs
  peers, −11.48 pp vs last year; Yunchuan 2025-07 own −6.07 pp but YoY −0.80 pp.
- The live-LLM writer is optional and **not enabled** in this build (`llm_configured: false`). The offline
  deterministic writer is the demo path; `.env.example` documents the optional provider settings.
